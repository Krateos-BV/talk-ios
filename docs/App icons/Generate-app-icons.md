# App icon and brand glyph

There is no PNG export step any more. The app icon is a vector source that Xcode
composes at build time, and the raster brand assets that carry the same glyph are
generated by a script in this repository. Nothing here needs Inkscape.

## The app icon

`NextcloudTalk/AppIcon.icon` is an Icon Composer bundle (`folder.iconcomposer.icon`),
referenced by `ASSETCATALOG_COMPILER_APPICON_NAME = AppIcon` and added to the app and
extension targets as a resource. It is the **only** app-icon source in the build —
`AppIcon.appiconset` was deleted in XNT-106 because it never shipped.

Two files:

| File | What it holds |
| --- | --- |
| `icon.json` | The background fill, and the position of each layer over it |
| `Assets/Talk-white.svg` | The Xenia two-bubble glyph, in a 24x24 `viewBox` |

Xcode renders every platform size from those at build time. Do not add PNGs.

### Changing the icon

Edit the SVG for the mark's shape, `icon.json` for how it sits on the background.

`icon.json` describes a linear-gradient `fill`, then one group holding the
`Talk-white` layer with a `shadow` and `translucency`. The layer's `position` takes
a `scale` and a `translation-in-points`. Measured on the 152pt render:

- `scale` is linear at roughly **2.07px per unit** (35 → 72px wide, 42 → 87px, 50 → 104px).
- `translation-in-points` moves the glyph only about **0.14px per point** — far weaker
  than the name suggests.

So a large centring correction belongs in the SVG's own coordinates, not in
`translation-in-points`: where the glyph sits in the rendered icon is driven mostly by
where its bounding box sits inside its own `viewBox`.

### Verifying a change locally

CocoaPods is not needed for this. `AppIcon.icon` compiles on its own:

```
xcrun actool NextcloudTalk/AppIcon.icon --compile <outdir> \
  --platform iphonesimulator --minimum-deployment-target 18.0 \
  --app-icon AppIcon --output-partial-info-plist <outdir>/p.plist
```

That writes `AppIcon60x60@2x.png`, `AppIcon76x76@2x~ipad.png` and an `Assets.car`.
On XNT-92 the `AppIcon76x76@2x~ipad.png` produced this way was byte-identical to the
same file in the CI build artifact for the same commit, so this is an authoritative
loop — use it instead of pushing and waiting for CI.

To compare a change, compile the old and new sources into two directories and diff the
renders. Measure the glyph by its bounding box over *neutral light* pixels
(`alpha > 128 and r > 150 and (b - r) < 45`); a plain brightness threshold also catches
the light top of the background gradient and reports a box pinned to the frame corner.

## The raster brand assets

The same glyph appears in several imagesets that are PNG, not vector. Those are
generated — never hand-edited — by:

```
python3 scripts/xenia-glyph-render.py
```

Run it from the repository root. It needs Pillow, which is not installed system-wide
on a stock macOS; a throwaway virtualenv is enough:

```
python3 -m venv /tmp/glyph-venv && /tmp/glyph-venv/bin/pip install Pillow
/tmp/glyph-venv/bin/python scripts/xenia-glyph-render.py
```

### How the script is laid out

The geometry constants at the top express the same three shapes as `Talk-white.svg`,
in the same 24x24 frame: `RECT_UPPER`, `RECT_LOWER` and `TAIL`, with `GLYPH_BOX` as
their tight bounding box. **`Talk-white.svg` and these constants must agree** — they
are two hand-maintained copies of one design, and they have drifted apart before
(XNT-131 fixed the SVG keeping a pre-XNT-101 tail long after the script had moved on).
`Icons/talk.svg` is a third copy, hand-written from the same numbers.

`ASSETS` maps each imageset name to its canvas size, the glyph's width, and a fill
colour. Read that table in the file rather than trusting a list here. Two conventions
hold across its rows:

- **Footprint is preserved.** Each asset keeps the alpha bounding box of the artwork it
  replaced: measure the old PNG's alpha box at @3x, divide by three, and use that as the
  glyph width. The Xenia mark is wider than it is tall, so matching width leaves a new
  asset slightly shorter than the round mark it replaces. That is expected.
- **Fill colour is often cosmetic.** For several of these only the alpha channel reaches
  the screen. Every `talk-20` call site re-renders it either `.alwaysTemplate` or with an
  explicit `withTintColor`, and every `*-placeholder` goes through
  `PlaceholderView.setImage`, which forces `.alwaysTemplate` and tints with
  `NCAppBranding.placeholderColor()`. For those the fill is chosen to match sibling assets
  at source level, and nothing more.

Rendering is supersampled 16x and downsampled with a box filter. That is deliberate: the
supersample factor is an exact integer, so a box filter is plain area averaging, while
Lanczos has negative lobes that ring a faint halo of non-zero alpha past the glyph and
quietly widen its bounding box.

### Adding an asset to the script

1. Measure the existing artwork first — canvas size at 1x, and the alpha bounding box at
   @3x — and take the fill from the pixels rather than assuming white.
2. Add the row to `ASSETS` and re-run the script.
3. Annotate the new PNGs in `REUSE.toml`. Redrawn artwork goes in the **XeniaCloud**
   block, not the Nextcloud trademark one: nothing Nextcloud-derived survives in a file
   the script produced.

`logo-action` is deliberately **absent** from `ASSETS`. It sits beside "Open in
Nextcloud" and identifies the Nextcloud app, so XNT-117 restored the upstream mark there;
adding it back to the table would silently undo that.

### A trap when re-running the script

Re-running it rewrites every PNG, and some come back byte-different but pixel-identical —
Pillow encoder and metadata drift between versions, not a geometry change. Before
committing anything you did not mean to touch, compare pixels rather than bytes:

```python
from PIL import Image, ImageChops
ImageChops.difference(Image.open(old).convert("RGBA"),
                      Image.open(new).convert("RGBA")).getbbox()   # None == identical
```

and `git checkout -- NextcloudTalk/Images.xcassets` to drop the noise.

## Verifying in the built app

`xenia-ci.yml` builds against the simulator SDK and uploads `NextcloudTalk.app`, so the
artifact can be installed on a simulator with `xcrun simctl install` to see an icon or a
glyph in place. To preview an asset change without a build, recompile the catalogue and
swap it into the installed bundle:

```
xcrun actool NextcloudTalk/Images.xcassets NextcloudTalk/AppIcon.icon --compile <out> \
  --platform iphonesimulator --minimum-deployment-target 18.0 \
  --app-icon AppIcon --output-partial-info-plist <out>/p.plist
cp <out>/Assets.car <path to>/NextcloudTalk.app/Assets.car
```

Note that a byte scan of `Assets.car` for a colour proves nothing — Xcode compiles
imagesets into binary renditions, so the hex string never appears — and small rasters are
packed into shared `ZZZZPackedAsset-*` atlases whose digests do not move when their
contents change. Compile a single imageset in isolation if you need a digest to be
meaningful, and check pixels directly otherwise.
